# The Strategy Operating System — Diagnose → Map → Choose → Execute → Govern → Communicate

A reusable engagement backbone: twenty modular strategy plays plus one master mode that chains them. Each play is the set of questions a good strategy partner asks, packaged so you run them deliberately rather than from memory. Pull a single play off the shelf when that is all the problem needs; run the full six-stage cycle when the decision is big enough to earn it — a market entry, a turnaround, a bet-the-quarter investment.

This module is an operating layer on top of the rest of the library. Every play ends with a **Connects to** line pointing at the deeper reference files that expand the framework, the math, or the delivery craft. Treat this file as the spine and those files as the muscle.

## How to run these plays

1. **A play is a deliberate move, not a script.** You are the consultant; these are the moves you make. Do not narrate "here is a prompt" — just run the procedure and produce the output.
2. **Fill in the real situation.** Replace every `[bracket]` with the actual company, market, decision, and numbers. Specific and honest in, sharp out; vague in, vague out. Where you have raw data, reason over it directly.
3. **Lead with structure, then quantify.** Turn a qualitative ask into an issue tree plus an explicit quantified spine — show the arithmetic (ratios, unit economics, sensitivities), never restated facts. Label any invented figure `[ILLUSTRATIVE]` and sanity-check the math.
4. **Treat the first pass as a draft to argue with.** The insight almost always arrives in the second or third exchange. Each play carries a **Push one level deeper** move that forces it. Use it.
5. **Flag thin evidence honestly.** Say where you are inferring versus where the data is solid, and name what the user would have to verify before trusting a number.

## The engagement backbone

| Stage | What you do | Plays |
|-------|-------------|-------|
| **01 · Diagnose** | Frame the real problem, baseline the situation, audit the load-bearing assumptions | 01–03 |
| **02 · Map** | Map the market and value chain, read the rivals, segment the customers, locate the profit | 04–07 |
| **03 · Choose** | Generate genuinely distinct options, price, build the case, prune the portfolio | 08–11 |
| **04 · Execute** | Design the operating model, prioritise the backlog, sequence the roadmap | 12–14 |
| **05 · Govern** | Run the risks, war-game the plan, build the KPI scorecard | 15–17 |
| **06 · Communicate** | Align stakeholders, build the narrative, write the decision memo | 18–20 |
| **Operate** | Chain all six stages into one disciplined cycle | 21 |

Run the cycle in order for a major decision, pausing at each stage to feed back what you learned so the analysis compounds. For everything smaller, lift a single play off the shelf.

## DIAGNOSE · Problem-Framing Plays (01–03)

Most strategy work fails here — by solving a crisp version of the wrong problem. Start under the symptom, name the decision in play, and stress-test the beliefs the whole case rests on.

### 01 · Problem-Framing
> Turn a vague concern into one specific, decision-oriented question; separate the symptom you can see from the cause you need to fix.

**Reach for it when** the brief is a topic ("our retention problem") rather than a question, or when the team is already arguing about solutions.

**The frame**
- Restate the problem as a single answerable question, not a topic.
- Split the presenting symptom from the likely root cause.
- Fix scope: what is in, what is deliberately out.
- Name the decision the analysis must enable, and who owns it.

**Run it — produce:**
1. The core problem restated as ONE specific, decision-oriented question.
2. The presenting symptom separated from the likely root causes underneath it.
3. Scope: what is in, and what is deliberately left out.
4. The decision this analysis must enable, and who makes it.
5. What would have to be true for this to be the *right* problem to solve.
Push back if the framing is too narrow, too broad, or a solution in disguise.

**Push one level deeper:** offer two alternative framings a sharp colleague might argue for instead, and the condition under which each would be the right one to pursue.

**Quality bar:** if the restated problem feels obvious, it was framed well. If it feels surprising, the wrong thing was being solved.

**Connects to:** `references/problem-solving.md`, `references/mckinsey-style-problem-solving.md`, `references/first-principles-thinking.md`

### 02 · Situation Assessment
> Build a fast, structured baseline broken into clean, non-overlapping pieces so nothing important hides in the gaps.

**Reach for it when** the question is clear and you need a structured baseline before all the data is in — so you know exactly what to go and find.

**The frame**
- Decompose the question into a MECE issue tree.
- For each branch, note what you would need to know and the fastest way to learn it.
- Identify the few branches that actually drive the answer.

**Run it — produce:**
1. The core question broken into 3–5 mutually exclusive, collectively exhaustive branches.
2. One level of sub-branches under each.
3. For every leaf, (a) what you would need to know and (b) the fastest way to find out.
4. The 2–3 branches most likely to drive the answer — the 80/20.
Keep branches genuinely non-overlapping; flag any branch where information is thin.

**Push one level deeper:** for each driving branch, draft the specific analysis or data pull that would resolve it, ranked by effort against insight.

**Quality bar:** draw the tree as nested bullets first, then pressure-test whether the branches overlap before going deeper.

**Connects to:** `references/issue-hypothesis-trees.md`, `references/mckinsey-style-problem-solving.md`, `references/structured-case-approach.md`

### 03 · Assumption Audit
> Surface the beliefs the plan quietly depends on, rank them by the damage a wrong one would do, and design the cheapest test for each.

**Reach for it when** you are about to commit to a recommendation, or a plan feels persuasive but you cannot quite say why you believe it.

**The frame**
- Extract every load-bearing assumption, stated or implied.
- Plot each on impact versus confidence.
- Find the killer assumptions: if false, the recommendation collapses.
- Design the cheapest, fastest test for the few that matter.

**Run it — produce:**
1. Every load-bearing assumption, including the unstated ones.
2. Each plotted on impact (high/low) by confidence (high/low).
3. The killer assumptions that, if false, break the whole case.
4. For the top 3, the cheapest and fastest way to validate or kill each.
Be skeptical; assume the user is more optimistic than the evidence warrants.

**Push one level deeper:** for the single most dangerous assumption, design a one-week test runnable with the data and access realistically at hand, and state what result would change the recommendation.

**Quality bar:** the dangerous assumptions are usually high-impact *and* high-confidence — the ones everyone is sure about and no one has tested.

**Connects to:** `references/hypothesis-invalidation-discipline.md`, `references/first-principles-thinking.md`, `references/mental-models.md`

## MAP · Market & Competitive Intelligence Plays (04–07)

Do not just summarise a market. Map where value pools, how rivals will move, and where the white space sits — the outside-in picture before you commit to a direction.

### 04 · Market Mapping
> Lay out the full market structure end to end: the boundary, the value chain, the size of each piece, and the adjacencies worth a look.

**Reach for it when** entering a new category, or when leadership argues about size and opportunity without a shared picture of where value sits.

**The frame**
- Define the market boundary and the adjacent markets next door.
- Map the value chain and note who captures margin at each stage.
- Size it: TAM, SAM, SOM, with assumptions on the table.
- Spot the white space and the structurally attractive niches.

**Run it — produce:**
1. The market boundary and the adjacent markets around it.
2. The value chain from input to end customer, noting who captures margin at each stage.
3. A rough size — TAM, SAM, SOM — with every assumption stated and the arithmetic shown.
4. The white space and the structurally attractive niches.
Where data is thin, say so clearly so the user knows what to verify.

**Push one level deeper:** rank the adjacencies and white-space niches by attractiveness *and* fit with existing capabilities, and name which to investigate first.

**Quality bar:** any market size is a starting hypothesis with assumptions attached, not a fact — always show the arithmetic.

**Connects to:** `references/guesstimation.md`, `references/guesstimates-and-frameworks-quantified.md`, `references/industry-heuristics.md`, `references/universal-business-analysis.md`

### 05 · Competitive Intelligence
> Profile rivals' positions and economics, then predict their next moves from the logic of their own business model — not generic SWOT filler.

**Reach for it when** you are about to make a move rivals will react to, or "the competition" is discussed as a vague threat rather than specific players with specific economics.

**The frame**
- Five Forces: rate each force and explain what drives it.
- Profile the top rivals: position, cost structure, strategic intent.
- Predict each rival's next moves and the trigger that would prompt them.
- Locate where you are most, and least, defensible.

**Run it — produce:**
1. Porter's Five Forces with each force rated and the specific mechanism driving it.
2. The top 3–4 competitors profiled: positioning, cost structure, likely strategic intent.
3. For each, the next 1–2 moves and the trigger that would set them off.
4. Where you are most defensible and where you are most exposed.
Avoid generic statements; tie every point to a concrete mechanism or piece of evidence.

**Push one level deeper:** pick the rival most likely to disrupt you and war-game their most aggressive plausible move over the next twelve months, plus the signal that would tell you it is coming.

**Quality bar:** the most useful output is a predicted competitor move plus its trigger — that is what lets the user watch for it in real life.

**Connects to:** `references/competitive-intelligence.md`, `references/industry-intelligence.md`, `references/scenario-planning.md`, `references/frameworks.md`

### 06 · Customer Segmentation
> Segment by what drives buying behaviour and value — the job to be done — not just age and postcode, then rank segments by how winnable they are for you.

**Reach for it when** "the customer" is treated as one homogeneous group, or before you split spend across segments that may not deserve equal weight.

**The frame**
- Segment by needs and behaviour, not demographics alone.
- For each: the core job to be done, willingness to pay, cost to serve.
- Add your right to win in each segment.
- Rank by value × winnability; pick where to focus.

**Run it — produce:**
For each segment: the core job to be done, willingness to pay, cost to serve, and your right to win. Then rank segments by value × winnability, recommend the 1–2 to prioritise and which to deprioritise, and name the data needed to confirm segment sizes.

**Push one level deeper:** for the top 1–2 segments, sketch the value proposition and the proof points each would need to switch to you, and where that differs from what you say today.

**Quality bar:** a segment you can win beats a bigger segment you cannot — weigh right-to-win as heavily as size.

**Connects to:** `references/pricing-strategy.md`, `references/product-management-toolkit.md`, `references/competitive-intelligence.md`, `references/universal-business-analysis.md`

### 07 · Profit Pool Analysis
> Find where the money actually is along the value chain, and where it is quietly migrating, so you target pools that are deep and getting deeper.

**Reach for it when** revenue and profit point in different directions, or before you decide which part of the chain to own, partner, or exit.

**The frame**
- For each value-chain stage, estimate pool size and margin.
- Show where profit concentrates today.
- Identify where profit is migrating, and why.
- Recommend which pools to target or defend.

**Run it — produce:**
1. For each stage, the pool size (revenue) and average margin.
2. Where profit concentrates today across the chain.
3. Where profit is migrating, and the force behind it — technology, regulation, consolidation, changing demand.
4. Which pools to target or defend, and why.
State the assumptions behind any numbers so they can be sanity-checked.

**Push one level deeper:** show where profit migrates over the next 3–5 years and the structural force driving the shift, then name the pool to move toward now.

**Quality bar:** the biggest revenue stage is often not the most profitable — profit pools reveal where to play; revenue alone misleads.

**Connects to:** `references/corporate-strategy.md`, `references/industry-heuristics.md`, `references/value-creation-measurement.md`, `references/competitive-intelligence.md`

## CHOOSE · Strategic Choice Plays (08–11)

Strategy is choice, and choice means trade-offs. Generate genuinely distinct paths rather than three flavours of one, then weigh economics, sensitivities and risk before recommending a move you can defend.

### 08 · Strategic Option Generation
> Produce a handful of genuinely different strategic bets — not variations on a theme — then compare them honestly on payoff, feasibility and risk.

**Reach for it when** the team has quietly converged on one answer, or the "options" on the table are really one plan flanked by two strawmen.

**The frame**
- Generate 3–4 genuinely distinct options, plus a do-nothing baseline.
- For each: the thesis, what must be true to win, investment, risks, payoff.
- Compare in a single trade-off table.
- Recommend one, and say what would change the recommendation.

**Run it — produce:**
1. 3–4 genuinely distinct options — different bets, not flavours of one — including a "do nothing" baseline.
2. For each: core thesis, what must be true to win, investment required, key risks, expected payoff.
3. A side-by-side trade-off table.
4. A recommendation with reasons, and the new information that would change it.
If two options are really the same bet, collapse them and find a genuinely different one.

**Push one level deeper:** stress-test the preferred option against the strongest alternative — under what conditions does the choice become the wrong one?

**Quality bar:** if every option points to the same answer, there are no options — deliberately surface one path the user will not like.

**Connects to:** `references/frameworks.md`, `references/scenario-planning.md`, `references/decision-making-under-uncertainty.md`, `references/corporate-strategy.md`

### 09 · Pricing Strategy
> Set price from the value the customer actually gets and the economics underneath — not a cost-plus reflex — and propose an architecture of tiers that captures it.

**Reach for it when** you are setting or revisiting price, or discounting has become the reflex and nobody can say what the offer is actually worth.

**The frame**
- Estimate economic value to the customer versus their next-best alternative.
- Compare cost-plus, competitive and value-based approaches; pick one.
- Design a price architecture: tiers, bundles, fences.
- Model scenarios and flag the pricing risks.

**Run it — produce:**
1. The economic value to the customer versus their next-best alternative.
2. Cost-plus vs competition-based vs value-based pricing compared, with one recommended and why.
3. A price architecture (tiers or bundles) and the logic behind the fences between them.
4. 2–3 scenarios with rough volume and margin implications.
5. The pricing risks: cannibalisation, channel conflict, perception, discount leakage.

**Push one level deeper:** model the revenue and margin impact of the top two structures at conservative, base and optimistic adoption, and show the break-even on each.

**Quality bar:** get the value-based number first — cost-plus tells you the floor; value tells you the ceiling you are leaving on the table.

**Connects to:** `references/pricing-strategy.md`, `references/pricing-architecture-consulting.md`, `references/pricing-revenue-management.md`, `references/quantitative-toolkit.md`

### 10 · Business Case
> Build a rigorous, defensible case an exacting CFO would respect: costs, benefits, timing, returns, sensitivities, and an honest downside.

**Reach for it when** you are about to take an investment to a decision forum, or enthusiasm for an initiative has run ahead of the arithmetic.

**The frame**
- Lay out costs and benefits over the horizon.
- Compute NPV, ROI and payback at a stated discount rate.
- Run sensitivity on the two or three variables that matter most.
- Show base, upside and downside cases; state what gets challenged first.

**Run it — produce:**
1. Costs (one-time and ongoing) and benefits (quantified where possible) over `[N]` years.
2. NPV, ROI and payback at a stated discount rate.
3. A sensitivity analysis on the 2–3 variables that move the result most.
4. A base case, an upside case and a downside case.
5. The assumptions a skeptical CFO would challenge first.
Be conservative — better to be surprised on the upside than caught short.

**Push one level deeper:** run the sensitivity on the two or three variables that move NPV most, and name the single assumption a skeptical CFO would attack first.

**Quality bar:** the sensitivity analysis is the whole game — a case that only works in the base scenario is not a case, it is a hope.

**Connects to:** `references/value-creation-measurement.md`, `references/quantitative-toolkit.md`, `references/tools-and-analysis.md`, `references/decision-making-under-uncertainty.md`

### 11 · Portfolio Review
> Decide where to invest, hold, harvest or exit across a set of products or units, and force the uncomfortable calls that have been avoided.

**Reach for it when** resources are spread thin across too many products, units or initiatives, and somehow everything is a priority.

**The frame**
- Plot each unit on a 9-box: market attractiveness by competitive strength.
- Classify into invest, hold, harvest, divest.
- Reallocate resource from low to high potential.
- Check across Three Horizons so the future is not starved.

**Run it — produce:**
1. Each unit plotted on a 9-box grid (market attractiveness × competitive strength), with how each axis was scored.
2. Each classified into invest / hold / harvest / divest.
3. How to reallocate resource from low- to high-potential units.
4. The portfolio mapped across Three Horizons (core today, emerging, future bets) to check the future is not being starved to feed the present.
Be willing to recommend killing or selling something — name which.

**Push one level deeper:** for every "maintain" or "exit" call, name the trigger or threshold that would change the decision, so the review holds up when someone pushes back.

**Quality bar:** the hardest part of a portfolio review is the divest list — if it is empty, ask what you would stop to free up 20%.

**Connects to:** `references/corporate-strategy.md`, `references/pe-context.md`, `references/frameworks.md`, `references/value-creation-measurement.md`

## EXECUTE · Execution Plays (12–14)

Strategy that cannot be delivered is a slide, not a plan. Turn a chosen direction into capabilities, owners, decision rights, phases and a concrete first 90 days.

### 12 · Operating Model Design
> Translate a strategy into the structure, capabilities, processes and decision rights needed to deliver it, and name the changes that will be hardest.

**Reach for it when** a direction is chosen and you need to make it real in capabilities, structure and decision rights — before anyone reorganises a thing.

**The frame**
- Identify required capabilities; sort into have, build, buy.
- Define structure, key roles and how work flows.
- Set decision rights with a simple RACI.
- Choose the governance and the metrics that matter.

**Run it — produce:**
1. The capabilities required, and which you have today versus must build or buy.
2. The structure and the key roles.
3. The core processes and how they connect.
4. Decision rights via a simple RACI: who decides what.
5. Governance and the handful of metrics that actually matter.
Flag the 2–3 hardest changes and why they will be hard.

**Push one level deeper:** name the 2–3 hardest changes, who will resist each and why, and the first move that would build momentum.

**Quality bar:** most operating-model failures are decision-rights failures — be specific about who *decides*, not just who is involved.

**Connects to:** `references/operating-model-translation.md`, `references/decision-rights-architecture.md`, `references/org-design-workforce.md`, `references/capability-assessment-talent.md`

### 13 · Initiative Prioritisation
> Rank a crowded backlog by impact and effort, map the dependencies, and give a sequenced shortlist that respects how much the team can actually do.

**Reach for it when** the backlog is longer than the team can deliver, or sequencing is being driven by whoever lobbies hardest.

**The frame**
- Score each initiative on impact and effort (plus fit and risk if useful).
- Plot on an impact-effort matrix: quick wins, big bets, money pits.
- Map dependencies: what must come before what.
- Recommend a sequenced shortlist under real capacity limits.

**Run it — produce:**
1. Each initiative scored on impact and effort (add strategic fit and risk if relevant), with the criteria and any weights shown.
2. An impact-effort matrix naming the quick wins, the big bets and the money pits.
3. The dependencies: what has to happen before what.
4. A sequenced shortlist, given you cannot do everything at once.
Challenge any pet project that does not earn its place on impact alone.

**Push one level deeper:** map dependencies across the shortlist, state what must finish before what, and give a realistic first-quarter sequence under actual capacity.

**Quality bar:** quick wins buy the credibility and momentum to fund the big bets later — sequence them first, on purpose.

**Connects to:** `references/transformation-program-architecture.md`, `references/implementation-practitioner.md`, `references/benefits-realization-tracking.md`, `references/product-management-toolkit.md`

### 14 · Transformation Roadmap
> Sequence a large change into phases with clear exit criteria, owners and milestones, and spell out the first 90 days in real detail.

**Reach for it when** a strategy needs to become a time-phased plan with owners and milestones, or the transformation has no concrete first ninety days.

**The frame**
- Break into phases, each with an objective and exit criteria.
- Define workstreams and an owner for each.
- Lay milestones on a dependency-aware timeline.
- Detail the first 90 days; name the change risks.

**Run it — produce:**
1. 3 phases, each with a clear objective and exit criteria.
2. The workstreams, each with an owner.
3. Milestones on a timeline, sequenced around their dependencies.
4. The first 90 days in specifics: who does what, by when.
5. The top change-management risks and how to mitigate them.
Be realistic about pace — a plan you can hit, not an aspiration.

**Push one level deeper:** pressure-test the roadmap for the dependency or resourcing assumption most likely to slip, and name the earliest signal that it is slipping.

**Quality bar:** exit criteria per phase are what stop a transformation from drifting — "we will know phase one is done when…" should be unambiguous.

**Connects to:** `references/transformation-program-architecture.md`, `references/implementation-practitioner.md`, `references/implementation-pmo.md`, `references/change-management.md`

## GOVERN · Risk & Value Governance Plays (15–17)

Pressure-test the strategy before the market does, then build the scorecard that tells you whether the value you promised is actually being captured.

### 15 · Risk Mitigation
> Identify what could go wrong across every angle, rank it, and pair each serious risk with both a way to make it less likely and a plan if it happens anyway.

**Reach for it when** a plan is about to go live, or the conversation is all upside and nobody has named what could go wrong.

**The frame**
- Build a risk register across strategic, operational, financial, external.
- Rate each likelihood by impact, and rank.
- For the top risks: a mitigation and a contingency.
- Assign an owner and an early-warning indicator for each.

**Run it — produce:**
1. The material risks across four angles: strategic, operational, financial, external.
2. Each rated on likelihood × impact, then ranked.
3. For the top risks, both a mitigation (reduce the probability) and a contingency (reduce the damage if it happens).
4. An owner and an early-warning indicator for each.
5. One non-obvious, left-field risk the user is probably ignoring.

**Push one level deeper:** for the top three risks, write the early-warning indicator and the pre-agreed response, so the team acts on signal instead of arguing once it has already happened.

**Quality bar:** mitigation lowers the odds; contingency limits the damage — serious risks need both, not one or the other.

**Connects to:** `references/erm-quantitative-risk.md`, `references/scenario-planning.md`, `references/regulatory-intelligence-horizon-scanning.md`, `references/decision-making-under-uncertainty.md`

### 16 · War-Gaming
> Play the strategy out against intelligent, adversarial competitor and market responses across several rounds, so you find where it breaks in a workshop, not in the market.

**Reach for it when** you are about to make a competitive move, a launch or a negotiation and need to know how the plan breaks in a room rather than on a slide.

**The frame**
- Role-play the key actors: you, your main rival, the customer.
- Run action and reaction over several rounds.
- After each round, note where your plan is exposed.
- End with the most dangerous response and how to harden against it.

**Run it — produce:**
Play 3 actors — us, our main competitor, the customer/market — over 3 rounds: we move, they react, we counter. After each round, note where the plan is exposed. End with (a) the single most dangerous competitor response, (b) the assumption of ours it exploits, and (c) how to make the strategy more robust. Play a genuinely adversarial opponent — to win, not to flatter.

**Push one level deeper:** run a second round assuming the first response provoked the competitor's sharpest counter — where does the position break, and how do you harden it now?

**Quality bar:** play the competitor as smart and ruthless — a soft opponent teaches you nothing.

**Connects to:** `references/scenario-planning.md`, `references/competitive-intelligence.md`, `references/situation-room-facilitation.md`

### 17 · KPI Architecture
> Build a coherent metric tree from a single north-star down to the operational drivers people can actually move, and weed out the vanity metrics.

**Reach for it when** a strategy has no scorecard, or the dashboard is full of numbers nobody ever acts on.

**The frame**
- Define the north-star metric and why it is the right one.
- Build the driver tree down to controllable operational metrics.
- Mark leading versus lagging; set targets and thresholds.
- Call out vanity metrics and gaming risks; keep the dashboard small.

**Run it — produce:**
1. The north-star metric and why it is the right one.
2. The driver tree down to operational metrics people can actually control.
3. For each metric, leading vs lagging, plus a target and red/amber/green thresholds.
4. The vanity metrics to avoid and any way each metric could be gamed.
Keep the top-level dashboard to roughly 7 metrics — if it is longer, it is not a dashboard.

**Push one level deeper:** trace each north-star metric down to the 2–3 operational drivers a team can move this quarter, and flag any metric that is easy to game.

**Quality bar:** for every metric ask "who can move this, and how?" — if the answer is fuzzy, it is a vanity metric in disguise.

**Connects to:** `references/value-creation-measurement.md`, `references/benefits-realization-tracking.md`, `references/board-communication-and-decision-support.md`, `references/data-visualization.md`

## COMMUNICATE · Executive Communication Plays (18–20)

The best analysis dies if it cannot survive a board meeting. Turn the work into a Pyramid Principle story, rehearse the hostile questions, and produce a one-page recommendation a busy executive can act on.

### 18 · Stakeholder Alignment
> Map who holds power and interest, where each person stands, and the one message that moves the people you most need on side.

**Reach for it when** a decision needs buy-in from people who do not all want the same thing, or a sound recommendation keeps stalling.

**The frame**
- Plot stakeholders on a power-interest grid.
- Mark each as champion, neutral, skeptic or blocker; note what they care about and fear.
- Craft the single message that moves each high-power stakeholder.
- Sequence the coalition you need to build.

**Run it — produce:**
1. The key stakeholders plotted on a power × interest grid.
2. Each marked champion / neutral / skeptic / blocker, with what they care about and what they fear.
3. For each high-power stakeholder, the one message most likely to move them.
4. A sequence for building a winning coalition.
Be candid about who to neutralise, not only who to win over.

**Push one level deeper:** draft the one sentence to say to each high-power stakeholder to move them — in their language and their priorities, not yours.

**Quality bar:** sequence matters — line up champions before confronting blockers, so no one walks into the room alone.

**Connects to:** `references/stakeholder-mapping.md`, `references/client-political-mapping.md`, `references/tactical-empathy-trust.md`, `references/behavioral-change-design.md`

### 19 · Narrative Builder
> Turn a pile of analysis into a clear, answer-first story using the Pyramid Principle, so the logic lands before the audience gets lost in the data.

**Reach for it when** you have the analysis but the story is not landing, or the deck is a pile of findings with no spine.

**The frame**
- State the single governing thought — the answer — up front.
- Support it with three MECE key arguments.
- Put the evidence under each argument.
- Write it as a storyline first, slides later.

**Run it — produce:**
1. The single governing thought (the answer) at the very top.
2. Three mutually exclusive, collectively exhaustive key arguments supporting it.
3. The evidence under each argument.
4. A one-page storyline — the "so-what" flow, not a data dump.
5. A tightened 60-second spoken version.
Lead with the answer, not the background; assume an impatient audience.

**Push one level deeper:** tighten to a 30-second version that leads with the answer, then name the one chart that has to be on the page for it to be believed.

**Quality bar:** if you cannot say the answer in the first sentence, you do not yet have one — the pyramid forces it out.

**Connects to:** `references/pyramid-principle-and-scqa.md`, `references/storylining.md`, `references/output-craft.md`, `references/structured-verbal-communication.md`

### 20 · Decision Memo
> Produce a crisp, one-page, board-ready recommendation with the ask up front, and rehearse the toughest questions before you walk in.

**Reach for it when** a decision needs a crisp one-pager a busy executive can act on, or the recommendation is buried on slide thirty-four.

**The frame**
- Recommendation first, in one or two sentences.
- Context, options considered, rationale, risks.
- The specific decision or approval you are asking for.
- A hostile Q&A: the toughest questions, answered.

**Run it — produce:**

## OPERATE · The Reusable Consulting Operating System (21)

### 21 · The Full-Cycle Engagement
> Run all six stages in order on a single decision, pausing at each stage for the user's input, so the same disciplined spine carries from the real problem to a board-ready recommendation.

**Reach for it when** the decision earns the full cycle — a market entry, a turnaround, a bet-the-quarter investment. For everything smaller, lift a single play off the shelf.

**Run it — move through six stages, pausing at the end of each for the user's input before continuing:**

1. **Diagnose** — reframe the real problem (01), give a MECE situation assessment (02), and audit the load-bearing assumptions (03).
2. **Map** — map the market and value chain (04), profile the competitors and their likely moves (05), segment the customers (06), and locate the profit pools (07).
3. **Choose** — generate 3–4 genuinely distinct options (08), price (09) and build the case (10) where relevant, prune the portfolio (11), and recommend one.
4. **Execute** — turn the choice into an operating model (12), a prioritised initiative list (13), and a phased roadmap with a concrete first 90 days (14).
5. **Govern** — build a risk register (15), war-game the strategy against an adversarial competitor (16), and design a KPI scorecard to track value capture (17).
6. **Communicate** — map the stakeholders (18), build a Pyramid Principle narrative (19), and write a one-page decision memo with a hostile Q&A (20).

At every stage, flag where the user's information is thin and where you are inferring. Challenge weak thinking. Let the output of each stage feed the next so the analysis compounds. Start with stage 1.

**Quality bar:** the value is in running the same backbone every time and pausing to feed learning forward — not in producing six disconnected artifacts in one pass.

## Five principles that travel

These carry across every play, and they are the difference between a structured first draft and a decision you can defend.

1. **Start with the real problem.** A crisp answer to the wrong question is the most expensive thing you can produce.
2. **Make every number show its arithmetic.** A figure you cannot trace is a guess in a good suit.
3. **Argue with the first draft.** The insight almost always arrives in the second exchange, not the first.
4. **Name what would change your mind.** Decide the disconfirming evidence before you fall for the answer.
5. **Keep the judgement the client's.** These plays widen the options and test the logic; the call still belongs to the decision-maker. The point is sharper thinking, not outsourced judgement.

## Appendix — paste-ready prompts

When a user wants to drive a play themselves (paste straight into a fresh chat), these are the self-contained versions. They are the same plays above, phrased as instructions the user gives Claude. Fill the `[brackets]` and paste real context alongside.

**01 · Problem-Framing** — "Act as a strategy partner. Before solving anything, reframe my problem. Situation: `[what is happening and why it is on the agenda]`. (1) Restate the core problem as ONE specific, decision-oriented question. (2) Separate the presenting symptom from the likely root causes. (3) Define scope — what is in, what we are deliberately leaving out. (4) State the decision this must enable, and who makes it. (5) Tell me what would have to be true for this to be the RIGHT problem to solve. Push back if I have framed it too narrowly, too broadly, or as a solution in disguise."

**02 · Situation Assessment** — "Run a situation assessment using a MECE issue tree. Context: `[business, question, what I already know]`. (1) Break the core question into 3–5 mutually exclusive, collectively exhaustive branches. (2) Add one level of sub-branches under each. (3) For every leaf, note (a) what we'd need to know and (b) the fastest way to find out. (4) Finish with the 2–3 branches most likely to drive the answer — the 80/20. Keep branches non-overlapping; flag any branch where my information is thin."

**03 · Assumption Audit** — "Audit the assumptions in this plan: `[paste the plan or thesis]`. (1) Extract every load-bearing assumption, including the unstated ones. (2) Plot each on impact (high/low) by confidence (high/low). (3) Identify the killer assumptions that, if false, break the whole case. (4) For the top 3, propose the cheapest and fastest way to validate or kill each. Be skeptical; assume I am more optimistic than the evidence warrants."

**04 · Market Mapping** — "Map the market for `[product or category]` in `[geography]`. (1) Define the market boundary and adjacent markets. (2) Lay out the value chain from input to end customer, noting who captures margin at each stage. (3) Size it roughly — TAM, SAM, SOM — with every assumption stated. (4) Identify the white space and structurally attractive niches. Where my data is thin, say so clearly."

**05 · Competitive Intelligence** — "Analyse the competitive landscape for `[company]` in `[market]`. (1) Porter's Five Forces — rate each force and explain the specific mechanism driving it. (2) Profile the top 3–4 competitors: positioning, cost structure, likely strategic intent. (3) For each, predict their next 1–2 moves and the trigger that would set them off. (4) Identify where we are most defensible and most exposed. Tie every point to a concrete mechanism or piece of evidence."

**06 · Customer Segmentation** — "Build a customer segmentation for `[business]`. Segment by needs and behaviour, not just demographics. For each segment give me: the core job to be done, willingness to pay, cost to serve, and our right to win. Then rank segments by value × winnability, recommend the 1–2 to prioritise and which to deprioritise, and tell me what data I'd need to confirm segment sizes."

**07 · Profit Pool Analysis** — "Do a profit pool analysis for the `[industry]` value chain. (1) For each stage, estimate pool size (revenue) and average margin. (2) Show where profit concentrates today. (3) Identify where profit is migrating and the force behind it — technology, regulation, consolidation, changing demand. (4) Recommend which pools we should target or defend, and why. State the assumptions behind any numbers."

**08 · Strategic Option Generation** — "Generate strategic options for `[decision]`. (1) Produce 3–4 genuinely distinct options — different bets, not flavours of one — including a 'do nothing' baseline. (2) For each: core thesis, what must be true to win, investment required, key risks, expected payoff. (3) Lay them side by side in a trade-off table. (4) Recommend one, explain why, and tell me what new information would change your recommendation. If two options are really the same bet, collapse them and find a genuinely different one."

**09 · Pricing Strategy** — "Recommend a pricing strategy for `[product]`. (1) Estimate the economic value to the customer versus their next-best alternative. (2) Compare cost-plus, competition-based and value-based pricing, and recommend one with reasons. (3) Propose a price architecture (tiers or bundles) and the logic behind the fences. (4) Model 2–3 scenarios with rough volume and margin implications. (5) Flag the pricing risks: cannibalisation, channel conflict, perception, discount leakage."

**10 · Business Case** — "Build a business case for `[initiative]`. (1) Lay out costs (one-time and ongoing) and benefits (quantified where possible) over `[N]` years. (2) Compute NPV, ROI and payback at a stated discount rate. (3) Run sensitivity on the 2–3 variables that move the result most. (4) Show a base, upside and downside case. (5) List the assumptions a skeptical CFO would challenge first. Be conservative."

**11 · Portfolio Review** — "Review this portfolio of `[products or business units]`: `[list them]`. (1) Plot each on a 9-box grid (market attractiveness × competitive strength) and state how you scored each axis. (2) Classify each into invest / hold / harvest / divest. (3) Recommend how to reallocate resource from low- to high-potential units. (4) Map the portfolio across Three Horizons to check we are not starving the future. Be willing to recommend killing or selling something — tell me which."

**12 · Operating Model Design** — "Design an operating model to deliver this strategy: `[paste the strategy]`. Cover: (1) the capabilities required, and which we have today versus must build or buy; (2) the structure and key roles; (3) the core processes and how they connect; (4) decision rights via a simple RACI; (5) governance and the handful of metrics that matter. Flag the 2–3 hardest changes and why they'll be hard."

**13 · Initiative Prioritisation** — "Prioritise these initiatives: `[list them]`. (1) Score each on impact and effort (add strategic fit and risk if relevant); show the criteria and any weights. (2) Plot them on an impact-effort matrix and name the quick wins, big bets and money pits. (3) Map the dependencies: what has to happen before what. (4) Recommend a sequenced shortlist, given we cannot do everything at once. Challenge any pet project that does not earn its place on impact alone."

**14 · Transformation Roadmap** — "Build a transformation roadmap for `[program]`. (1) Break it into 3 phases, each with a clear objective and exit criteria. (2) Define the workstreams and assign an owner to each. (3) Lay the milestones on a timeline, sequenced around dependencies. (4) Detail the first 90 days: who does what, by when. (5) Name the top change-management risks and how to mitigate them. Be realistic about pace."

**15 · Risk Mitigation** — "Build a risk register for `[plan]`. (1) List the material risks across four angles: strategic, operational, financial, external. (2) Rate each on likelihood × impact, then rank. (3) For the top risks, give both a mitigation and a contingency. (4) Assign an owner and an early-warning indicator to each. (5) Add one non-obvious, left-field risk I am probably ignoring."

**16 · War-Gaming** — "War-game this strategy: `[paste the strategy]`. Play 3 actors — us, our main competitor, and the customer/market. Run 3 rounds: we move, they react, we counter. After each round, note where our plan is exposed. End with (a) the single most dangerous competitor response, (b) the assumption of ours it exploits, and (c) how we'd make the strategy more robust. Be a genuinely adversarial opponent — play to win."

**17 · KPI Architecture** — "Design a KPI architecture for `[objective]`. (1) Define the north-star metric and why it's the right one. (2) Build the driver tree down to operational metrics people can actually control. (3) For each metric, mark leading vs lagging and set a target plus red/amber/green thresholds. (4) Call out the vanity metrics to avoid and any way each metric could be gamed. Keep the top-level dashboard to roughly 7 metrics."

**18 · Stakeholder Alignment** — "Build a stakeholder map and alignment plan for `[initiative]`. (1) List the key stakeholders and plot them on a power × interest grid. (2) Mark each as champion / neutral / skeptic / blocker, and note what they care about and fear. (3) For each high-power stakeholder, craft the one message most likely to move them. (4) Recommend a sequence for building a winning coalition. Be candid about who I need to neutralise, not only who I can win over."

**19 · Narrative Builder** — "Turn this analysis into an executive narrative using the Pyramid Principle: `[paste the analysis]`. (1) State the single governing thought (the answer) at the very top. (2) Support it with 3 mutually exclusive, collectively exhaustive key arguments. (3) Under each, lay out the evidence. (4) Write it as a one-page storyline — the 'so-what' flow, not a data dump. (5) Give me a tightened 60-second spoken version. Lead with the answer."

**20 · Decision Memo** — "Write a one-page decision memo for `[decision]`. Structure: (1) recommendation in 1–2 sentences, first; (2) context and why now; (3) options considered and why we rejected the others; (4) key risks and mitigations; (5) the specific decision or approval I am asking for. Then add a 'Hostile Q&A': the 5 toughest questions an executive will ask, each with a crisp answer. Keep it to one page."

Move through these six stages in order, and pause at the end of each for my input before continuing: (1) DIAGNOSE — reframe the real problem, give me a MECE situation assessment, and audit the load-bearing assumptions. (6) COMMUNICATE — map the stakeholders, build a Pyramid Principle narrative, and write a one-page decision memo with a hostile Q&A. At every stage, flag where my information is thin and where you are inferring. Challenge me when my thinking is weak. Start with stage 1."
